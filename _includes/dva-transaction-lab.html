One voucher, two writes — what if the second fails?

Transfer voucher V-42: delete Alice's ownership item, then put Bob's. A transaction makes both changes one atomic unit. A batch makes individual writes atomic, but allows partial success. This is a conceptual local model; the order of actual batch execution is not guaranteed.

  1. AliceOwns V-42
  2. Write boundaryTransaction: all-or-nothing
  3. BobNo voucher

Failure under a transaction: Alice keeps V-42; Bob receives nothing. Failure under a batch: Alice's delete may persist while Bob's put remains unprocessed.

# Conceptual SDK pseudocode; two distinct ownership items
TransactWriteItems([
  Delete(AliceVoucher, condition="owner = Alice"),
  Put(BobVoucher, condition="attribute_not_exists(PK)")
])
# BatchWriteItem supports Put/Delete, no conditions or Update.

ACID: Atomicity = all or nothing; Consistency = declared conditions/invariants remain valid when correctly modelled; Isolation = concurrent transactions behave serialisably for supported transactional operations; Durability = committed changes persist. Both APIs are synchronous requests. Returning immediately vs waiting is independent of atomicity. A strongly consistent GetItem reads a recent committed item; it does not atomically coordinate multiple changes. Two independent strongly consistent reads are not one multi-item snapshot; use TransactGetItems for an atomic read set.
